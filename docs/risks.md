# Risks

Review at every status checkpoint. Include API/model failures, rate limits, internet, latency, hallucination, integration, demo, time, and scope risks when relevant.

| ID | Risk | Likelihood | Impact | Trigger / early signal | Mitigation | Fallback | Owner | Status |
|---|---|---|---|---|---|---|---|---|
| RISK-001 | SSE is treated as authoritative somewhere in the code, causing displayed/decided state to diverge from simulator truth. | Medium | High | Dashboard shows stale/wrong numbers after a `stream_disconnect` or queue-overflow test. | Hard rule: every SSE handler only triggers a REST re-GET, never reads business fields off the SSE payload. Code review checklist item. | Disable SSE entirely and fall back to REST polling only; document as acceptable per guide. | Team | OPEN |
| RISK-002 | Idempotency key collisions or reuse-after-cancel bugs cause duplicate or rejected allocations under retry. | Medium | Medium | 409 IDEMPOTENCY_KEY_MISMATCH appears unexpectedly during load test or fault injection. | Generate keys as `{our-run-id}-{monotonic-counter}` or UUID per intended allocation, never reused across retries with different bodies. | Manual key inspection tool in admin/debug view. | Team | OPEN |
| RISK-003 | Fault injection (`unavailable`/`error_rate`/`latency`) during judging causes visible crashes instead of demonstrating resilience. | Medium | High | Any unhandled exception or blank UI during a fault-injection demo segment. | Build and rehearse resilience paths (REQ-009) before demo; wrap all simulator calls in retry/backoff/timeout with graceful degraded-mode UI state. | Manually pause fault injection via `/admin/faults/clear` if live demo destabilizes; narrate the intended behavior from logs/metrics instead. | Team | OPEN |
| RISK-004 | Two client error envelope shapes (`{"detail":...}` vs `{"error":...}`) are not both handled, causing error parsing to throw. | Medium | Medium | Uncaught exception in simulator-client error path during 503 fault. | Central simulator-response parser normalizes both shapes into one internal error type. | N/A — should be fixed before demo. | Team | OPEN |
| RISK-005 | Frontend setup (Vite, WebSocket wiring, charts) consumes the schedule before real data flows. | Medium | High | >2 hours with no live simulator data on screen. | Frontend builds against a mocked Core contract in parallel (SPEC.md Phase 3); timebox scaffolding. | Cut charts to tables; keep status grid, alerts, recommendation review. | Frontend | OPEN |
| RISK-006 | Demand-history table grows unboundedly and an unbounded/no-`limit` query is used somewhere, causing slow responses or memory pressure during a long-running demo. | Low | Medium | Slow `/v1/demand-history` calls late in a demo session. | Always call with an explicit `limit` and a bounded recent window; document the chosen window. | N/A | Team | OPEN |
| RISK-007 | Chosen intelligence capability produces a technically-correct but operationally useless recommendation (e.g., ML accuracy without decision usefulness). | Medium | High | Judges question "why does this matter" and demo has no answer. | Anchor intelligence work to REQ-008 (inspectable recommendation with expected impact) from the start, not accuracy metrics alone. | Fall back to a transparent rule-based/heuristic allocation policy with a clear rationale string — still satisfies REQ-007. | Team | OPEN |
| RISK-008 | Stack/architecture decision is delayed past the point where implementation time is safely available. | Medium | High | ADR-002 still PROPOSED after research/architecture planning session ends. | This planning step ends with an explicit request for human approval; do not start implementation until ADR-002 is ACCEPTED. | Default to the recommended option in `docs/decisions.md` if no response within an agreed time box (team must set that time box). | Team | OPEN |
| RISK-009 | Load test itself becomes a source of instability during judging window (e.g., run live against the only simulator instance right before demo). | Low | Medium | Load test run scheduled too close to demo start. | Run and capture load-test evidence well before the demo slot; do not re-run live unless explicitly asked. | Present recorded/previous load-test evidence per `docs/verification.md`. | Team | OPEN |
| RISK-011 | Infrastructure breadth: about 8 containers (simulator, core, intelligence, frontend, Postgres, Redis, Prometheus, Grafana) is more than the minimal design and adds startup-order and config failure modes right before a live demo. | Medium | High | `docker compose up` fails or takes long on a clean machine; a dependency container unhealthy. | DevOps owns Compose healthchecks and depends_on conditions from Phase 0; test clean-machine startup repeatedly. | Cut order in `docs/cut-list.md`: Grafana, then Redis, before touching product or intelligence. | DevOps | OPEN |
| RISK-012 | Deterministic idempotency key collides or replays the wrong outcome: quantity not in hash, or a FAILED allocation retried under the same key returns the failed record. | Medium | Medium | 409 `IDEMPOTENCY_KEY_MISMATCH`, or a retried allocation silently stays FAILED. | ADR-004 refinements: include quantity/route in the hash, add an attempt counter. Unit-test replay, mismatch, and post-FAILED retry. | Manual key override in a debug endpoint. | Integration | OPEN |
| RISK-013 | Intelligence Service becomes a single point of failure or a latency source for Core. | Medium | Medium | Recommendation latency rises or errors when Intelligence is restarted. | Core calls it with a timeout and circuit breaker; fallback heuristic works without it. | Core-local heuristic. | Integration + Intelligence | OPEN |
| RISK-014 | LLM narration is slow, fails, or hallucinates numbers not in the recommendation object. | Medium | Medium | Narration text contradicts the structured fields; timeouts at demo. | Pass only the finished recommendation object; render numbers from the object, not the LLM; timeout plus template fallback. | Templated explanation. | Intelligence | OPEN |
| RISK-010 | Organizer-introduced "surprise" domain/engineering events during judging (Problem §1 dynamic) hit an untested code path. | Medium | Medium | New event/fault type or unexpected sequencing appears live. | Build resilience generically (validate-and-degrade-safely by default) rather than special-casing only the fault/event types we tested. | Explicit "unknown event — flagged for human review" behavior instead of crashing or silently ignoring it. | Team | OPEN |
